# GMTK2026 塔防 V0 — 机制总结与路线图

> 项目路径：`D:\unity\GMTK2026塔防V0`  
> 引擎：Unity 2022.3（2D）  
> 文档用途：对齐三人小组对「当前雏形」与「后续要做」的共识  

---

## 1. 游戏愿景（一句话）

**电路解谜 + 像素塔防**：玩家在下方 7×7 棋盘上搭建能量球回路，用能量驱动攻击模块，防守上方单路线的怪物；胜利靠精巧的弹道/能量编排，而不是传统固定炮塔摆位。

---

## 2. 完整设计中的核心机制（目标态）

### 2.1 画面分区

| 区域 | 占比（设计） | 职责 |
|------|--------------|------|
| 上方战斗区 | ~20% | 怪物右→左；最左魔法师；触碰扣血，血尽失败 |
| 下方建造区 | ~80% | 7×7 棋盘 + 右侧商店 + 底部手牌 |

### 2.2 能量球总线

- 触发器在棋盘**外侧**（入口格左侧）定时向右发射能量球。
- **所有攻击/特效模块必须被能量球命中后才工作**。
- 球有飞行速度、寿命、全场数量上限；飞出棋盘即失效。
- 进阶方向（未做）：球带「能量质量/类型」（白/橙/紫等），炮塔按各自规则把能量翻译成攻击。

### 2.3 模块两大类

**逻辑改造类**（改球的路径与属性）

- 转向 / 收束器（90° 弯道）
- 分流、筛选
- 中继（续命、接力）
- 增速 / 减速
- 射速增幅（改触发器频率）

**攻击输出类**（被触发后打上方怪物）

- 飞弹、火焰、雷电、冰冻、穿刺等
- 特效约定：攻击线连接**棋盘模块世界坐标 ↔ 战斗单位世界坐标**（跨分区），不是只在战斗条内播动画。

### 2.4 伪无限构筑（设计原则）

- 追求「看起来永动、满盘刷球」的爽感，但必须有寿命/衰减/上限，避免真无限导致无敌与卡顿。
- 深度来自多种闭环原理（几何环、节拍续命、储能喷发、召回复用、共生等），而非只有「拐弯 + 分裂」。

### 2.5 对局循环（目标态）

初始金币 → 买模块铺盘 → 球循环触发输出 → 清怪赚钱 → 优化回路 → 守住魔法师通关波次。

## 3. 当前雏形已实现什么

运行入口：`GameBootstrap`（Play `SampleScene` 会自动组装整局）。

### 3.1 已具备的系统一览

| 系统 | 状态 | 说明 |
|------|------|------|
| 场景分区 UI | ✅ | 战斗 HUD + 棋盘 + 右侧商店占位 + 底部手牌 |
| 7×7 棋盘 | ✅ | `(0,0)=左下`；放置/占用查询 |
| 棋盘外发射器 | ✅ | 对准入口 `(0,3)` 左侧；每 2s 向右发球；**不占格** |
| 能量球 | ✅ | 能量恒定 1；速度/寿命；上限 40；出界销毁 |
| 格心触发 | ✅ | 越过格心才触发；触发前贴格心再改向 |
| 收束器 | ✅ | 可旋转 90° 弯道；四朝向双向连通口 |
| 射弹塔 | ✅ | 储能上限 10；有能量每 0.1s 耗 1 点打最左敌人，伤害 5；跨区拖尾线 |
| 静止靶子 | ✅ | 右上战斗区；只挨打、不移动 |
| 伤害统计 | ✅ | `Total Damage` HUD |
| 手牌放置 | ✅ | 上限 5；从商店购入；点选 → 点格放置；`R`/右键旋转 |
| 商店 | ✅ | 6 槽随机刷新（当前仅两种模块）；点击免费入手；`F` 刷新；暂无金币 |

### 3.2 雏形核心循环（可演示）

```text
商店随机货架 → 点击免费购入到手牌（上限5）
     ↓
手牌选模块 → 摆到 7×7（可反复买→放，铺满棋盘）
     ↓
外侧发射器持续发球
     ↓
收束器在格心改向 → 射弹塔吸能
     ↓
射弹塔向战斗区靶子拉线造成伤害 → HUD 累计
```

`F`：刷新商店货架。
### 3.3 脚本结构（便于队友导航）

```text
Assets/Scripts/
  Core/       GridDirection, GridCoord, ModuleType, PrototypeSprites
  Board/      GridBoard, Emitter
  Ball/       EnergyBall, EnergyBallManager
  Modules/    ModuleBase, RedirectorModule, ProjectileModule
  Combat/     EnemyTarget, DamageTracker
  UI/         HandController, HandSlot, PlacementController, ShopPanelPlaceholder
  Game/       GameBootstrap
```

## 5. 三人分工建议

假设角色：**程序 A（核心）**、**程序 B（战斗/内容）**、**策划/美术 C**。

### 5.1 职责划分

| 角色 | 主责 | 协作边界 |
|------|------|----------|
| **程序 A** | 棋盘、能量球、模块接口、放置、回路规则、性能上限 | 提供 `ModuleBase` / 球状态 API；不擅自改战斗数值表 |
| **程序 B** | 怪物、波次、魔法师、胜负、金币结算、攻击特效表现 | 消费棋盘输出事件；不改球物理规则 |

### 5.3 协作约定（减少返工）

1. **模块规格先于代码**：每张模块写清「球进入 → 球离开 / 能量变化 / 是否消耗触发」。  
2. **收束器朝向表、发射器棋盘外坐标** 以代码注释为准，改规则先改文档再改实现。  
3. **上下坐标分离**：棋盘格索引 ≠ 战斗世界坐标；攻击只用世界坐标连线。  
4. **禁止真无限**：任何「续命/分裂」必须有硬上限，写入同一张平衡表。

## 7. 相关设计备忘（已讨论、待落地）

- **受控伪无限**：视觉可满屏，逻辑有寿命/衰减/球上限。  
- **攻击差异靠「能量解释」**：飞弹吃次数、火焰吃维持、雷电吃蓄爆、狙击吃高质量球——避免所有炮塔只比 DPS。  
- **多种闭环原理**：几何环、节拍续命、储能喷发、召回复用、交换共生——避免只有「拐弯+分裂」。
